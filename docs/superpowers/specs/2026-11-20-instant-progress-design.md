# 진도표 버튼 즉시 반영 (짧은 설계)

## 왜
통과·학생 추가를 누르면 5초쯤 기다려야 한다. 측정: 시트 목록 읽기 1.8~2.4초, 통과 = 기록 요청(2~3초) + 목록 다시 읽기(약 2초). 시트는 사람이 보기만 하고 고치지 않는다.

## 목표 / 아닌 것
- 목표: 통과·재시험·↶·학생 추가·수정·삭제를 누르면 화면이 즉시 바뀌고, 시트 저장은 뒤에서.
- 아닌 것: 시트 구조·Apps Script 변경, 다른 저장소로 이전, 실제 저장 시간 단축.
- 실패로 치는 것: 화면과 시트가 몰래 어긋난 채로 남는 것, 저장 중 창을 닫아 기록이 사라지는 것.

## 방법 비교
- **A. 시트 유지 + 화면 먼저 (선택)** — 작고 지금 구조 그대로. 실제 저장은 여전히 2~3초.
- B. Firebase 등 빠른 저장소 — 실제로 빠르지만 계정·이전·권한·시트 동기화가 필요, 일이 몇 배.
- C. GitHub 비공개 저장소 — PC마다 토큰, 동시 쓰기 충돌, 0.5~1.5초라 결국 A도 필요.
- D. 로컬(브라우저 / 학원 PC 서버) — 빠르지만 PC 간 공유 또는 상시 켜 둔 PC 문제.

"시트에서 필요한 줄만 고치기"는 뺌: 병합된 학년·교재 칸 때문에 줄 끼워 넣기가 "병합된 셀의 일부" 오류를 냄. 저장이 뒤에서 처리되니 느려도 상관없음 (Code.gs 그대로, 재배포 없음).

## 동작 (app.js만)
1. 버튼을 누르면 칸·다음 범위·목록을 바로 바꾸고, 상태 줄에 "저장 중 N건".
2. 저장 요청은 한 줄로 세워 하나씩 보낸다. 요청은 보내는 순간의 행 번호(r)를 쓴다.
3. 통과·재시험·↶ 뒤에는 목록을 다시 읽지 않는다. 학생 추가·수정·삭제 뒤에만 뒤에서 다시 읽고, 다음 요청은 그 뒤에 보낸다.
4. 새로 추가한 학생은 목록에 바로 보이되 저장이 끝날 때까지 버튼 잠금.
5. 실패하면 남은 요청을 멈추고, 시트를 다시 읽어 실제 상태로 되돌리고, 빨간 글씨로 무엇이 실패했는지 알린다.
6. 저장 중에 창을 닫거나 새로고침하면 브라우저 경고 (beforeunload).
